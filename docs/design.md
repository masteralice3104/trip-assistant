# 旅補助アプリ 設計書

## 1. 文書の位置づけ

この文書は、旅行の計画から実行、予算管理までを支援するアプリの初期設計をまとめたものです。現時点では**設計段階であり、アプリのソースコードは未実装**です。ユーザーが確定した事項と、検討のための設計案・未決事項を区別します。技術構成、費用、外部サービスの利用可否は調査前のため、特定の方式を前提にしません。

## 2. ユーザー確定事項

- 一般向け公開を目標とし、自分用のカスタマイズも行う。
- GitHubでソースを公開する。
- PC・Web・Androidを主な利用環境とし、iOS対応は候補とする。
- 運営するWebサービスにログインし、PCとスマートフォンの間で旅行データを同期する。
- 旅行の計画、実行、予算立てまで一通り扱えるアプリを目指す。
- 「予約・予定・資料を探し直す手間」を最も減らしたい。ただし情報集約だけに機能範囲を限定しない。
- 主な情報源は、メモ、旅行サイト、航空会社サイト。

## 3. 設計の狙い（案）

旅行ごとに情報をまとめ、検討から旅行後の振り返りまでを一続きに扱う。候補、予定、予約、原本資料、URL、メモ、費用を相互に関連付け、必要なときに元の情報へすぐ戻れるようにする。計画変更と実際の予約変更は別の出来事として扱い、計画の編集だけで予約済みの内容が変わったように見せない。

想定する流れは「条件と予算を決める → 候補を比較する → 旅程と予約を管理する → 出発準備をする → 当日に確認する → 支出を記録して振り返る」。旅行の状況に応じて各段階を行き来できる構成とする。

### 情報の扱い

- 旅行に、日程・目的地・同行者などの基本情報を持たせる。
- 行き先や宿泊先などの候補は比較用として保存し、採用した予定や予約と区別する。
- 予定には日時、場所、移動や活動の内容をまとめる。予約には予約先、確認番号などの参照情報、予約状態、関連する資料をひも付ける。
- 資料は原本ファイル、URL、メモなどを旅行や予定・予約に関連付ける。アプリ内の要約や一覧から原本へ戻れることを基本とする。
- 最初の入力方法はURLとメモの貼り付けを基本案とする。旅行サイトや航空会社サイトからの自動取得は、対象サイトや規約、技術面を別途検証してから範囲を決める。

### 予算と費用

旅行の予算上限、予約前の見込み額、予約後の確定額、実際に支払った額を区別する。予約状態（未予約・予約済み・取消など）と支払状態（未払い・一部支払い・支払い済みなど）は独立して管理する。同じ費用項目の見積・予約確定・支払いは、履歴を残しつつ同一項目の状態更新として扱い、段階ごとに別費用として合算しない。比較時に採用しなかった候補の金額は旅行費用に含めない。

例：ホテルの見積もりが12,000円、予約確定額が13,000円、支払額が13,000円の場合、費用項目は13,000円として集計する。12,000円・13,000円・13,000円の3件を合算しない。

## 4. 画面構成案

- **旅行一覧**：旅行の概要、日程、予算状況、直近の予定を確認する。
- **旅行概要**：旅行全体の進行状況と、次に必要な準備を把握する。
- **計画と旅程**：候補の比較、採用した予定の作成・編集、日程の確認を行う。
- **予算**：予算上限、見込み、確定額、実支出を分けて確認する。
- **予約と資料**：予約状態と関連資料を一覧し、原本や元URLへ移動する。
- **当日表示**：当日の予定、予約情報、必要資料を素早く確認する。

PCでは候補や費用の比較・編集をしやすくし、スマートフォンでは当日の予定や予約情報をすぐ確認できることを重視する。どの画面から編集しても同じ旅行データを参照する。

## 5. データと公開範囲の考え方（案）

公開するソースコードと、利用者が登録する旅行データは別に扱う。旅行データはログインした利用者のアカウントに結び付け、個人設定（表示や入力の好みなど）を保持する。同期や保存の具体的な方式、共有機能、データ保護の詳細は今後設計する。リポジトリや公開サンプルに、認証情報や個人の旅行情報を含めない。

## 6. 未決事項

実装方針を固める前に、次の点を決める必要がある。

- オフラインで利用できる機能と、同期再開時の競合処理。
- 同行者との共有範囲、編集権限、招待方法。
- サイト情報の取り込みをどこまで自動化するか。対象サイトごとの技術的可否や利用条件。
- Androidの配布方法とネイティブアプリが必要かどうか。
- iOS対応の優先度。
- 国内旅行と海外旅行のどちらを先に重視するか。
- 複数通貨、為替換算、時差をどう扱うか。
- 技術スタック、サービス運用費、公開ライセンス。

これらは決定済みの仕様ではない。調査や利用者の優先順位を踏まえて選択する。

## 7. 初期の対象範囲

旅行単位の情報整理、計画・旅程、予約と資料の参照、予算と支出の一貫した管理、PCとスマートフォン間の同期を設計の中心に置く。予約や決済の手続きは、まず元サイトへ進む形を想定し、アプリ内での自動実行は別途検討する。サイト自動取得、共有、オフライン対応などは未決事項の判断後に範囲を定める。
